# Easy2GIF 内核检查报告

**2026-10-15 更新：本报告记录修复前基线的问题，F01–F16 的处理及验证见 [修复记录](kernel-fixes.md)。**

检查日期：2026-10-14。检查基线：`1a7dbb5`，`gifcore 1.0.0`，C ABI 6。

## 1. 结论与检查范围

内核的分层、全局调色板复用、按内存预算分批编码，以及先写临时 GIF 再替换目标文件的方向合理。现有测试能够证明常规输入下 GIF 容器和 LZW 编码可被第三方解码，多线程输出也具有确定性。

但目前存在影响画面正确性、选帧准确性和播放时间的实际问题。优先修复透明优化、视频流选择、缩略图尺寸推导、解码错误吞掉和帧延时计算，再优化线程池、文件读写与调色板搜索。**现有测试全绿不能代表这些功能已经正确。**

本次检查覆盖 `src/export.rs`、`src/ffmpeg/`、`src/gif/`、`src/ffi.rs`、`src/error.rs`、`src/platform.rs`，并核对 C ABI 头文件、C++ 桥接层的相关调用与现有测试。启动器和发布脚本不作为重点。没有修改业务实现。

优先级含义：P1 为影响输出正确性、应优先修复的问题；P2 为功能语义、边界、响应速度和稳定性问题；P3 为可随后处理的体验或维护问题。“已复现”表示执行过当前代码；“静态确认”表示代码路径已确认，未做完整运行复现；“条件风险”表示需要特定调用方式或外部条件。

## 3. 逻辑问题与修复建议

### F01 · P1：透明优化比较了原始前帧，而非实际显示画布【已复现】

位置：[export.rs](../src/export.rs)，`apply_transparency` 第 228 行、`stream_frames` 第 1210 行、`map_and_compress` 第 1384 行附近。

当前将本帧原始 RGB 与上一张原始 RGB 比较，然后把差异小的像素设为透明。透明意味着保留解码器画布上的旧颜色；这个颜色可能来自更早的帧。若每帧变化都在容差内，程序永远不更新该像素，累积变化可以无限扩大。

复现：32×32、10 fps、32 帧，每帧灰度依次为 `0, 4, 8, …, 124`；开启透明优化，容差 4。第三方回读结果如下：

| 设置 | 回读结果 |
| --- | --- |
| 关闭透明优化 | 灰度从约 2 逐渐变化到约 120，差异来自调色板量化 |
| 开启透明优化，容差 4 | 32 帧全部停留在灰度 2 |
| 再开启重复帧合并 | 合成 2 个 GIF 帧，但仍一直显示灰度 2 |
| 开启透明优化，容差 0，无抖动 | 此素材的回读像素与关闭优化一致 |

**容差为 0 也不能保证正确。** Floyd 抖动的像素索引受邻近像素误差影响；某个位置的原始 RGB 没变，其索引仍可能改变。另一个实验使用相同的 8 色映射调色板、只改变每行首列，开启透明优化后，回读结果与完整帧有 **3285/24576 个通道字节不同**，已排除调色板不同这一因素。

建议先并行完成各帧索引化，再按帧顺序与“已合成的索引/颜色画布”比较，生成透明差分并更新画布。零容差按实际索引判断；非零容差与实际显示颜色比较。另需统一容差定义：现在使用 `|ΔR|+|ΔG|+|ΔB| <= 3*tolerance`，并非头文件说明的每通道上限，例如容差 4 会放过单通道变化 12。

### F02 · P1：探测的视频流与实际解码的视频流可能不同【已复现】

位置：[probe.rs](../src/ffmpeg/probe.rs)，第 118–136 行；[frames.rs](../src/ffmpeg/frames.rs)，预览/胶片条命令；[export.rs](../src/export.rs)，`decode_args_at` 第 361 行。

探测固定选择第一个视频流；FFmpeg 命令没有 `-map`，会自动选择视频流。复现素材包含两个都未标记 default 的视频流：第一路 32×32 红色，第二路 64×64 绿色。内核探测返回 32×32，预览却返回绿色 `[0,127,0]`。

预览按探测尺寸截取解码字节，因此还会把较大帧当较小帧解释；导出则可能把另一条视频缩放为第一条视频的尺寸。另一个静态缺陷是 `if is_attached && found_video`：封面流排在首位时仍会被选中，后面的真实视频流被跳过。

建议在 `MediaInfo` 保存选定视频流的真实 `index`，所有解码命令统一使用 `-map 0:<index>`；无条件跳过 `attached_pic`，再应用一致的主视频选择规则。

### F03 · P1：胶片条高度舍入与 FFmpeg 不一致，导致错误分帧【已复现】

位置：[frames.rs](../src/ffmpeg/frames.rs)，第 140 行的 `scale=...:-2` 与第 177–221 行的尺寸推导。

FFmpeg 将高度舍入到相邻的偶数；Rust 先舍入到整数，再把奇数向上补一。这两种算法不等价。源码只在算出 `n == 0` 时尝试补救；多数尺寸错误仍能算出正数，因而直接切错。

复现：320×181、12 帧视频，胶片条参数 12 张、宽度 160。FFmpeg 实际输出 12 张 **160×90**；内核按 **160×92** 切分，返回 11 张，丢掉尾部字节，各缩略图跨越真实帧边界。时间戳数量不匹配后又被替换成均匀合成时间，最后一张标到了 1.2 秒，即素材末尾之外的帧边界。

建议由内核计算确定的目标宽高并显式传给 `scale=w:h`，或可靠读取 `showinfo` 的实际尺寸。要求原始字节总长能被单帧长度整除，否则返回错误；不要猜高度后接受余数。

### F04 · P2：预览 seek 会偏移帧，尾部选区还会解码为空【已复现】

位置：[frames.rs](../src/ffmpeg/frames.rs)，`decode_frame` 第 57–71 行；[ffi.rs](../src/ffi.rs)，`gif_update_poster` 第 617 行。

程序在用户时间上额外加半个帧间隔，再让 FFmpeg seek。FFmpeg 通常输出时间不早于 seek 点的第一帧，因此“加半帧”会越过原本目标。

在 F01 的 10 fps 素材中，0 秒预览得到第二帧灰度 4；0.051 秒得到第三帧灰度 8，仍应处于首帧显示区间；0.1 秒得到第三帧，而该时间应对应第二帧。3.19 秒仍处于视频时长 3.2 秒以内，但被 seek 到 EOF，返回 0 字节并报错。

缓存键按 `floor(time*fps)` 计算，而实际 seek 按原时间加半帧：同一缓存键内，不同请求本来就可能解出不同帧，缓存掩盖了这个不一致。

建议明确定义“时间点正在显示的帧”，让预览与导出共用时间语义；CFR 可按目标帧索引定位，VFR 应使用 PTS。尾部应落到最后一张可显示帧，而非仅钳制到 duration。验证时应比较具体像素，而非只验证缓冲区尺寸。

### F05 · P1：固定四舍五入延时会改变总时长，高帧率还会意外慢放【已复现】

位置：[export.rs](../src/export.rs)，第 593、646、697–698 行；估算中第 849、894 行有同样逻辑。

所有帧使用同一个 `round(100/play_fps)` 延时，误差会逐帧累积。同时采样率允许 120 fps，而播放率被钳制到 50 fps：帧数保留，播放时间被拉长。

| 输入设置，speed=1，选区 1 秒 | 实际帧数 | GIF 延时 | 实际播放时间 | 返回的 duration |
| --- | --- | --- | --- | --- |
| 30 fps | 30 | 每帧 3 cs | 0.90 秒 | 1.00 秒 |
| 60 fps | 60 | 每帧 2 cs | 1.20 秒 | 1.00 秒 |

`Outcome.fps` 返回的是舍入前目标值，例如 30，而实际等效播放率是约 33.33；`duration` 返回源选区长度，也没有反映 speed、丢帧或延时量化。

建议按累计目标时间分配整厘秒延时，例如 30 fps 使用 3/3/4 cs，控制总误差在约一厘秒内。2 cs 是本实现为播放器兼容采用的最低延时，不是 GIF 格式强制值；若维持该下限，应联合约束采样率与速度，或对超出上限的帧做重采样，并明确告知受限速度。分别返回源选区时长、实际 GIF 播放时长和实际时间统计。

### F06 · P1：解码器失败只要已经写过一帧，就被吞掉【已复现】

位置：[export.rs](../src/export.rs)，`decode_segments` 第 448–454 行。

这里不区分取消、写入失败和工具失败；只要 `written > 0` 就继续。估算的多个采样段共用 written，后续采样段完全失败也会被前一段的成功掩盖。

本次使用替代解码子进程：输出 4 个合法 RGB 帧，然后打印错误并以状态 1 退出。内核最终返回 **`Ok(Outcome)`**，产生 243 字节、4 帧的 GIF，只附带“请求 32 帧、实际提供 4 帧”的通用警告；真正的失败原因丢失。

建议正常 EOF 与明确失败分开。取消和 I/O 错误立即向上传递；非零退出默认失败。如果确实需要“抢救部分视频”，应作为显式设置，并保留原始失败原因和完整性状态。

### F07 · P2：“有序抖动”实际是弱化的 Floyd–Steinberg【已复现】

位置：[export.rs](../src/export.rs)，`FrameOptions::new` 第 210 行、`map_and_compress` 第 1381 行。

`Dither::Ordered` 与 `Dither::Floyd` 调用相同的误差扩散函数，唯一差别是前者强度乘 0.6。实验中“Ordered、强度 100”与“Floyd、强度 60”的 GIF **逐字节相同**。

这与界面的“有序/快速”及 `bayer` 别名不符，也没有真正获得有序抖动易并行、逐像素独立的性能特点。建议实现固定 Bayer 阈值矩阵并独立验证；若保留现算法，应把名字改为弱误差扩散。

### F08 · P2：抖动强度 0 在 C ABI 中变成 100【已复现】

位置：[ffi.rs](../src/ffi.rs)，`settings_from` 第 939–943 行；[gifcore.h](../include/gifcore.h)，`dither_strength`；桥接层允许 0–100。

为了零初始化兼容，ABI 把 0 解释为默认强度 100。界面却允许用户拖到 0，并把 0 原样传入。实验中强度 0 与 100 输出 **逐字节相同**；Rust 直接调用 `Settings` 时的 0 则可以关闭抖动，两个入口语义不同。

建议升级 ABI，以有效字段标志或保留值区分“默认”和“明确的 0”。默认 options 显式初始化为 100，界面传入的 0 必须得到 0。不要只改 UI 文案来掩盖该参数问题。

### F09 · P2：有损强度方向反了，而且建调色板没有使用有损后的像素【已复现 / 静态确认】

位置：[quantize.rs](../src/gif/quantize.rs)，`posterize_levels` 第 215 行、`posterize_in_place` 第 229 行；[export.rs](../src/export.rs)，`build_palette` 第 1411 行。

`levels = 1 + lossy*15/100` 被用于计算“保留的色阶数”；色阶越多，量化越细。实际结果：

| lossy | 每通道保留值数量 |
| --- | --- |
| 0 | 256，未处理 |
| 1 | 256，未处理 |
| 7 | 2，极强量化 |
| 50 | 8 |
| 100 | 16，反而比 7 更精细 |

因此 1–6 实际无效，7 附近突然发生强量化，继续加大又逐步减弱。另一个静态问题是 `build_palette` 没有接收 lossy 设置，仍用原始采样建调色板；只有逐帧映射前做 posterize。与“调色板、索引、帧间差分使用同一颜色”的注释不符。

建议用单调降低保留色阶的映射，让 0 保持原样；采样与正式映射共享同一预处理函数。最终体积还受抖动、素材和 LZW 影响，不能保证 lossy 增加时文件严格变小，但参数对颜色精度的影响必须方向一致。

### F10 · P2：取消不贯穿所有阶段，等待子进程时无法及时停止【静态确认】

位置：[export.rs](../src/export.rs)，第 502 行、第 1186 行、`build_palette`；[process.rs](../src/ffmpeg/process.rs)，第 438–458 行。

解码每写满 4 帧才检查取消；如果卡在阻塞读，取消无法打断。sink 出错后只关闭 stdout 再 `child.wait()`，没有显式终止子进程；不能假定所有子进程都会立即因管道关闭而退出。调色板采样、量化和色表查找阶段完全没有取消检查，已经取消的解码还会因 F06 进入分析阶段。

建议给整条作业传递独立取消令牌；入口及阶段边界检查取消，量化在迭代/分块之间检查；子进程管理支持取消、超时、终止并回收。区分 `Cancelled` 与 `Invalid` 错误，避免取消被误报为参数错误。

### F11 · P2：宽度限制可能被反向突破，高度没有 GIF 范围校验【已复现 / 静态确认】

位置：[export.rs](../src/export.rs)，`output_size` 第 330 行及第 1140、1394 行的 `as u16`。

极宽素材缩小后高度小于 2 时，代码先固定高度 2，再重新按比例扩大宽度，突破用户给出的最大宽度。直接调用复现：`MediaInfo{width:100000,height:2}`，max_width=480，得到 **(100000,2)**。最终写 GIF 时 `as u16` 又会截断尺寸；极窄长图则可能得到超过 65535 的高度。奇数宽度向上补偶数也可能超过奇数的 max_width。

建议一次性计算受两边上限约束的缩放结果，对尺寸和 `w*h*3` 使用 checked 运算，并在解码前验证 GIF 的 u16 范围与单帧资源预算。极端宽高比应允许小幅比例误差或明确拒绝，不应悄悄放大。

### F12 · P2：调色板采样并未真正铺满选区【静态确认】

位置：[export.rs](../src/export.rs)，`build_palette` 第 1427–1459 行。

使用 `stride = frame_count / target_frames` 的整数除法，并在取得 40 帧后提前结束。总帧数 79 时 stride=1，实际只采样 **0–39 帧**，几乎整个后半段被忽略；100 帧时只采样到 78，末尾也未覆盖。后半段出现独有颜色时，全局调色板可能严重失真。

像素预算同样使用向下取整。例如理论采样 299 万像素、预算 150 万时，pixel_stride 仍为 1，几乎超预算一倍。固定像素步长也可能与周期纹理对齐，形成采样偏差。

建议显式计算 `round(i*(N-1)/(K-1))` 的采样索引，覆盖首尾；像素步长使用向上取整。结合固定的二维分层采样，既控制预算，也维持重复导出确定性。

### F13 · P2：FFI 的作业互斥和 panic 边界不完整【条件风险】

位置：[ffi.rs](../src/ffi.rs)，`guard` 第 123 行、`gif_export_ex` 第 1014 行、`gif_estimate_size` 第 1073 行、预览发布函数。

导出和估算都直接 `running.store(true)`，没有原子抢占；同一 handle 被并发调用时，两项作业会共享并修改 progress、cancel、错误状态。后进入的作业还会清掉前项作业的取消请求。任意一项结束就把 running 置 false，即使另一项仍在运行。**当前 C++ 桥接层会排队，降低了正常 UI 的触发概率；内核 API 本身没有保证互斥。**

`guard` 只转换 Result，未捕获 panic，`Running` 的注释却宣称 panic 会被 guard 捕获。release 配置 `panic=abort`，一旦出现内部 panic，整个应用会退出，无法依靠 RAII 恢复状态。

预览/胶片条从锁内取得媒体快照、锁外解码、再锁内发布；如果期间加载另一视频，旧结果可能写回新视频。返回的借用像素指针在锁释放后，也依赖调用方不并发重建数据。对外 Rust 函数用安全签名接收并解引用裸指针，缺少 `unsafe` 契约。

建议用 `compare_exchange` 拒绝同 handle 的重叠作业，或建立独立 Job 状态。发布预览时校验媒体 generation；清楚规定像素数据生命周期、销毁前等待作业结束和并发访问规则。优先消除可触发 panic 的输入/资源路径；如要求捕获内部 panic，应配合 `panic=unwind` 与真正的边界处理，不能只加 `catch_unwind` 而保留 abort。

### F14 · P2：固定临时文件名与覆盖保护存在竞争窗口【条件风险】

位置：[export.rs](../src/export.rs)，`check_output` 第 969 行、`encode_frames` 第 1030–1038 行；[process.rs](../src/ffmpeg/process.rs)，临时文件创建。

输出暂存名固定为 `out_path.with_extension("gif.part")`，通过 `File::create` 打开。两个内核实例写同一目标，或不同扩展名但相同文件主名时，可能互相截断/删除暂存文件。`overwrite=false` 只在暂存前检查 exists，之后目标被其他进程创建仍可能在 rename 时被覆盖。也没有防止输入路径与输出路径指向同一文件。

写权限探针只使用 PID 命名，会覆盖同名已有探针；TempFile 的 PID+序号只生成路径，没有原子创建。它们在并发、进程重启残留等情况下缺少文件所有权保证。正常导出失败清理 `.part`、通过 rename 替换目标的总体方向是正确的，应保留。

建议用唯一名称加 `create_new` 原子创建，RAII 清理本作业拥有的文件；无覆盖模式在最终提交时仍必须有原子保证。明确校验输入/输出文件身份。权限检查尽量前置到昂贵解码之前，同时仍处理最终写入失败。

### F15 · P2：大小估算对重复帧与跨采样段差分有系统偏差【已复现 / 静态确认】

位置：[export.rs](../src/export.rs)，`estimate_segments` 第 760 行、`estimate` 第 904–929 行。

分段采样比只取中段合理，但把 8 段连续拼接后编码，会把不相邻的段尾和下一段段首当相邻帧处理。16 帧样本的 15 次相邻关系里，7 次是人工跨段跳变，影响透明优化和重复帧合并统计。

更直接的问题是把压缩后 body 按原始帧数线性放大。静止素材开启 dedupe 后，文件主要取决于一次完整帧和累计延时，而非总原始帧数。实验：32×32、10 fps、10 秒静止视频，开启 dedupe，**估算 358 字节，实际 90 字节，约高估 3.98 倍**。

建议保留采样段边界，每段重置透明/合并状态，独立测量关键帧、段内差分、重复率，再分别外推。静止长片还应计入 u16 延时上限造成的拆帧。短选区完整测量的 exact 路径应保留；长片给出估计区间及采样信息更符合实际。

### F16 · P3：进度统计单位不一致，进度会回退或长期停滞【静态确认】

位置：[export.rs](../src/export.rs)，`Progress::fraction` 第 76 行、`build_palette` 第 1454 行、`flush_pending` 第 1108 行。

fraction 计算的是当前阶段比例，却注释为总体进度，每换阶段都会归零。分析阶段 total 是总帧数，实际每采到 8 帧才加一；编码阶段 total 是输入帧数，而 dedupe 开启时按写出的 GIF 帧加一。100 张重复帧最终写 1 帧，进度可能长期约 1%，然后突然到 100%。

建议统一按处理的输入帧统计工作量，分别提供阶段进度和整体进度；调色板按采样/迭代计数，并定义适当的阶段权重。

## 4. 值得优化的地方

### O01：减少原始帧落盘和重复扫描

当前导出先把整个选区写成 RGB24，再为采样读一遍，最后编码再读一遍。480×270、12 fps、10 分钟的 raw 文件约 **2.61 GiB**；1920×1080、30 fps、1 分钟约 **10.43 GiB**。峰值 RAM 受控，但磁盘空间、I/O 与首帧导出等待随片长线性增加。

低风险改进是对 raw 文件按确定的帧偏移 `seek` 读取调色板样本，避免为了少量样本顺序扫过大量未使用帧。后续可评估“先解码样本建全局调色板，再流式完整解码+编码”，以第二次解码成本换取省磁盘；不能预设它对高解码成本素材也更快。长任务应提前计算预计暂存大小、设置上限并报告临时目录空间不足。

### O02：复用工作线程与每个 worker 的缓冲区

`encode_batch` 每批重新创建 scoped threads，`ColorMap::build_with_threads` 每次建查找表也重新创建线程。逐帧还分配 RGB、索引、六个抖动误差行、LZW key/value 表，并复制 block 到 pending；有损处理再复制一份 RGB，透明优化又复制 carry。

建议建立作业内持续存活的 worker，复用索引、抖动、LZW 和像素缓冲区。用所有权转移代替 `pending = Some(block.clone())`；dedupe 关闭时直接写 block。优先在小帧高帧率和大帧低批量场景测量收益，保持写出顺序与输出确定性。

当前 24 MiB 批预算也不等于严格的进程内存上限：每帧按两份 RGB 估计，却没有完整计入有损副本、carry、pending、压缩临时数据及所有线程的 scratch；超过预算的单帧仍会至少容纳一张。建议估算整个作业的峰值，并在极大帧上限制并发度。

### O03：消除不必要的颜色查找表构建

64³ 查找表在 256 色下每次约做 **6711 万次颜色距离比较**，确实是重计算。

`improve_with_kmeans` 在 iterations=0 时仍先建一次表；最后一次迭代颜色移动后仍建表，但离开函数后丢弃；导出又构建最终表。建议零迭代直接返回，避免最后一次无消费者的构建，评估同时返回最终 palette/map。若排序后复用 map，需要正确重映射索引，保持相同距离下的 tie-break，不能只复用旧索引。

Lloyd 累加实际上是整数通道值与整数计数，可使用 u64 分块累加后确定性合并，再计算均值；不必仅因为“浮点求和顺序会变化”就将整个采样归类阶段永久串行。需验证与旧输出的舍入结果兼容，并限制累计值范围。

### O04：改进量化质量与低颜色数量的快捷路径

Wu 分裂目前只在“跨度最大的轴”搜索切点，没有比较 RGB 三个轴的最佳方差收益。这是质量上的简化，可在三个轴搜索后选择总误差最小的切分，并拒绝空盒切分。

5-bit 直方图的单 bin 不再分裂，因此少量相近颜色也会被提前合并。实际调用 `quantize([0,0,0,4,4,4],256)` 只返回 `[[2,2,2]]`，后续 Lloyd 因只剩一个中心无法恢复。对源颜色数量本来就不多的画面，可先做精确颜色收集：未超过上限就直接保留，超过后再走 Wu。此项属于量化精度取舍，不是 GIF 容器错误。

量化测试目前主要比较查找表与“已有调色板的最优映射”，并不能充分证明调色板本身质量。建议用已知最优的小颜色集合、完整图像误差、渐变与真实素材作对照。

### O05：重复帧尽量在 LZW 前识别，透明差分使用变化矩形

dedupe 当前先完成全部映射与 LZW，再比较 frame block，主要省文件体积，没有省重复帧的压缩成本。先比较已映射索引、做 hash 筛选再精确比较，可避免重复 LZW；必须建立在 F01 修正后的显示语义上。

透明优化仍写全画布，`frame_block` 将 left/top 固定为 0。稀疏局部变化可计算最小变化矩形，只编码对应区域；无变化帧优先延长上一帧延时。需补充矩形偏移、边界、循环第一帧和 disposal 组合的第三方回读测试。

### O06：缓存媒体信息与可复用估算样本

handle 加载时已经 probe；每次估算和导出又 probe。默认一次估算还启动 8 个 FFmpeg 子进程。拖动设置时，丢弃旧结果仍不会停止旧作业，实际导出可能要等待过期估算结束。

建议内核接收/复用已验证媒体快照，以文件标识、大小和修改时间做失效判断；在采样时间、帧率、尺寸没有变化时，复用采样 RGB，颜色数、质量、抖动等变化只重跑必要阶段。估算采用独立 Job，并可取消已经过期的工作，避免占用正式导出。

### O07：加强媒体兼容性与公共辅助代码清理

目前按 width/height 推导显示比例，未处理 SAR；VFR 的帧号按平均 fps 计算；时长优先使用整个容器 duration，音轨比视频长时可能显示不可预览的尾部。这些属于静态兼容性风险，本次没有穷举对应素材。建议保存 SAR、视频流时长和时间戳语义，将精确帧号与基于平均 fps 的近似值区分。

JSON 解析器对非法 surrogate pair 没有校验低代理范围，可能发生下溢；也没有深度限制、有限数字校验和完整输入校验。正常 FFprobe 会生成合法 JSON，优先级低于实际媒体路径问题，可增加针对 parser 的模糊测试。Rust 导出入口的 fps/speed 等也应显式拒绝 NaN/Inf，比较大小并不等于验证有限数字。

`DataFile::open` 创建一个未落盘的新 TempFile 路径，然后立刻 `File::open`，通常必然失败；本次没有找到业务调用。`Frame::as_rgb32` 的实际字节布局是 RGBA，与注释中的 `0xffRRGGBB` 整数布局不是同一个概念。建议移除未使用辅助接口或澄清其契约，避免后续误用。

## 5. 建议实施顺序与验收条件

| 阶段 | 工作 | 关键验收 |
| --- | --- | --- |
| 第一阶段：输出正确性 | F01、F02、F03、F05、F06 | 透明优化零容差与完整帧回读一致；渐变误差有界；探测/解码选同一流；缩略图字节对齐；播放总时间受控；非零解码退出不报成功 |
| 第二阶段：参数与边界 | F04、F07–F11、F13–F14 | 时间与帧索引一致；Bayer 与 Floyd 为独立实现；强度 0 真正为 0；有损精度方向单调；取消贯穿所有阶段；尺寸不截断；并发作业和文件提交有明确定义 |
| 第三阶段：估算与性能 | F12、F15–F16、O01–O06 | 采样覆盖首尾；静止片估算偏差收敛；进度按工作量增长；记录每阶段耗时、峰值 RAM、暂存量、实际输出大小与误差 |

应补充的回归场景：多视频流且无 default、首流封面、奇数高度、末帧预览、30/60/120 fps 与 speed 组合、缓慢渐变透明容差、零容差抖动、强度 0、有损端点、79 帧后半段独有颜色、解码器部分输出后失败、分析中取消、跨批透明/去重、长静止片的延时溢出拆帧、同一目标并发提交。

性能比较应使用 release 构建，按素材/尺寸/颜色数/抖动模式分组，重复测量并报告中位数。现有性能测试要求多线程必然快于单线程，容易受调度噪声影响，适合移到独立基准；正确性测试继续要求各线程数输出字节一致。改变时间调度或算法时，旧版字节不同可能正是修复结果，应同时用第三方回读验证画面与播放时间。
